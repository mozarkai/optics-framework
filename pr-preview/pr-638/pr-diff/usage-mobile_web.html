tt1# Mobile Web (browsers and WebViews on Android and iOS)
2
3Optics drives web pages on Android and iOS devices through the same Appium session that
4drives native apps. One test can open an app, follow a link into Chrome or Safari, fill a
5web form, and come back to the app, with no separate browser driver and no context
6switching in your test steps. The same test steps work on both platforms.
7
8## How it works
9
10The Appium session stays in the native context the whole time. Native locators (visible
11text, resource ids, native XPath) and OCR keep working on web pages, because Chrome and
12Safari put the page's text, links, inputs and buttons into the native UI tree.
13
14Web locators, `css=...` and DOM XPath such as `//button[@type='submit']`, go through the
15`appium_web` element source. For each lookup it:
16
171. finds the web content of the app in front and its front tab: Chrome or a debuggable
18 WebView on Android; Safari, an in-app Safari sheet (`SFSafariViewController`), an
19 inspectable `WKWebView` or another inspectable browser on iOS,
202. finds the element in the page and scrolls it into view, closing the on-screen
21 keyboard if it covers the element,
223. converts the element's position to screen coordinates, and
234. returns to the native context.
24
25The press or text entry that follows is a native action at those coordinates.
26
27## Configuration
28
29Enable `appium_web` next to the other Appium sources. `optics quickstart` and
30`optics configure` enable it for Android and iOS projects, and the MCP server includes it
31when it fills in the Appium sources for you.
32
33```yaml
34driver_sources:
35 - appium:
36 enabled: true
37 url: "http://localhost:4723"
38 capabilities:
39 platformName: Android
40 automationName: UiAutomator2
41 deviceName: emulator-5554
42
43elements_sources:
44 - appium_find_element:
45 enabled: true
46 - appium_page_source:
47 enabled: true
48 - appium_web:
49 enabled: true
50 - appium_screenshot:
51 enabled: true
52```
53
54Web lookups use a chromedriver that matches the Chrome version on the device. Let
55Appium download it by starting the server with
56`appium server --allow-insecure uiautomator2:chromedriver_autodownload`, or point
57`appium:chromedriverExecutableDir` at a folder of chromedriver binaries.
58
59UiAutomator2 driver 8.6.0 or later converts element positions exactly, including pinch
60zoom. Older drivers work too: Optics computes the position from the page's
61geometry and the on-screen bounds of the WebView. For an app that shows several
62WebViews, use 8.6.0 or later, so each element is placed in the WebView that holds it.
63
64### iOS
65
66The same `elements_sources` work with `platformName: iOS` and `automationName: XCUITest`.
67No extra driver is needed; XCUITest reads web pages through Safari's Web Inspector.
68
69- **Real devices:** turn on **Web Inspector** and **Remote Automation** in
70 Settings > Apps > Safari > Advanced. Simulators need no setup.
71- **Apps:** a `WKWebView` is readable when the app sets `isInspectable = true`, which
72 apps built with the iOS 16.4 SDK or later need even in debug builds. Safari and in-app
73 Safari sheets are always readable.
74- **Other browsers:** Chrome, Firefox and other iOS browsers are read the same way when
75 they allow inspection. Chrome needs Settings > Content Settings > Web Inspector.
76
77Optics starts native iOS sessions with `includeSafariInWebviews: true`,
78`additionalWebviewBundleIds: ["*"]`, `webviewConnectRetries: 1` and
79`webviewAtomWaitTimeout: 5000` (values in your `capabilities` take precedence). They let
80it see every app's web content and keep a lookup on a page that cannot answer to seconds
81instead of minutes. Sessions that start in Safari (`browserName`) keep Appium's defaults.
82
83Web positions on iOS are converted to screen points from a measurement of the page on
84screen, so Safari's toolbars, page zoom and the keyboard are accounted for.
85
86## Opening pages
87
88`Launch App` and `Launch Other App` open a URL in the app that handles it, a browser
89for web addresses:
90
91```csv
92module_name,module_step,param_1
93Open Shop,Launch App,https://shop.example.com/
94Back To The App,Launch App,com.example.shop
95```
96
97In an app session the URL opens in the device's default handler: the default browser,
98or the app that owns the link. To open a web page in Chrome even when another browser is
99the default, call the deep link with Chrome's package:
100
101```csv
102module_name,module_step,param_1
103Open Shop In Chrome,Execute Script,"{""script"": ""mobile: deepLink"", ""args"": {""url"": ""https://shop.example.com/"", ""package"": ""com.android.chrome""}}"
104```
105
106To test only the browser on Android, start the session in Chrome by adding `browserName: Chrome`
107to the capabilities. Web addresses then open in that Chrome whatever the default browser
108is, and Optics moves the session to the native context as soon as it starts, so every
109keyword works the same way as in an app session.
110
111## Locators
112
113| Locator | Example | Resolved by |
114|---|---|---|
115| Visible text | `Sign in` | native tree, then OCR |
116| HTML id | `searchInput` | native tree (Chrome reports HTML ids as resource ids) |
117| CSS | `css=input[name='q']`, `#searchInput` | `appium_web` |
118| DOM XPath | `//button[@type='submit']` | native sources first, then `appium_web` (assertions skip the native sources for HTML-only paths) |
119
120An XPath that names an Android or iOS class (`android.widget.Button`,
121`XCUIElementTypeButton`) or a native attribute (`@resource-id`, `@content-desc`, `@text`,
122`@bounds`, `@clickable` and the other UiAutomator2 and XCUITest attributes) is left to the
123native sources. Text inside quotes does not count, so `//a[contains(@href,'android.com')]`
124is still a web locator. An assertion leaves an XPath whose path names only HTML
125elements (`//input[@name='email']`, `//button`) to `appium_web` alone; `//*` and other
126XPaths are still checked natively too. A web locator that matches an element hidden by the
127page (`display: none`, zero size) fails with "not displayed" instead of tapping blindly.
128A web locator that matches nothing fails at once, without waiting.
129
130`Assert Presence` with a web locator checks the DOM, so it passes for any element in the
131page, including one scrolled off screen or hidden. `Assert Visibility` passes only for an
132element that is displayed and inside the visible part of the page. An assertion checks
133every source that can take its locator in turn, round after round, until it passes or the
134timeout runs out, so the web check does not wait for the native sources to give up.
135
136## Screen elements
137
138`Get Interactive Elements`, `Get Screen Elements`, the MCP `elements` resource and the
139natural-language mode of `optics live` list the web page next to the app's native
140elements. With `appium_web` enabled, one call returns:
141
142- the native elements (Chrome's toolbar, the app around a WebView), as before;
143- every control and every piece of text of the web page, top to bottom, with screen-pixel
144 bounds. A sentence with links or bold words inside is one row, and the links get
145 their own rows; images, icons and canvases are listed too. Layout wrappers that hold
146 nothing of their own are left out. An element
147 outside the visible part of the page carries `offscreen: true`: scroll toward it, or
148 press it by locator, which scrolls it into view first;
149- a `loc` on each web element that the compact list reports (controls and visible
150 text): a `css=` or `xpath=` locator that matches only that element. Put it in your
151 elements file. The full list carries the same `loc` next to its `xpath`.
152
153The page's on-screen elements appear once. UiAutomator2 and XCUITest also show them in
154the native tree, without locators; the web entry replaces that copy.
155
156`loc` is built to stay the same from run to run. It uses, in order, a test attribute
157(`data-testid` and similar), a hand-written id, `name`, `placeholder`, `aria-label`,
158`title` or `alt`, a link's `href`, the element's own text, and a class. When those are
159shared, it names the element inside the card or row that holds it, for example
160`xpath=//article[.//h2[normalize-space()='Red Mug']]//button[normalize-space()='Add to cart']`.
161When nothing else is unique, it falls back to a CSS path. Generated ids and classes
162(`r-7f3a91c2`, `nav-help-83412`) are skipped. Text with digits, such as "Cart (0)", is
163matched by its leading words (`starts-with(normalize-space(), 'Cart (')`), so a count
164or a price that changes does not change the locator. The Playwright page source builds
165`loc` the same way.
166
167The listing adds about half a second on a local emulator, mostly finding and entering
168the page. On a screen with no web content, the cost is one check for web content.
169
170## Moving between apps and the browser
171
172Nothing in a test says which app is in front. Every lookup looks at the screen as it is
173now, so a test follows the user's path from one app to another:
174
175```csv
176module_name,module_step,param_1,param_2
177Read The Policy,Press Element,Google Play refund policy
178Read The Policy,Assert Presence,css=h1,30
179Read The Policy,Get Text,css=h1
180Read The Policy,Go Back
181Read The Policy,Assert Presence,Google Play refund policy,20
182```
183
184- **App to browser.** Tapping a link in an app opens Chrome or a Chrome Custom Tab, the
185 in-app browser most apps use. Web locators then find elements in the page in front, and
186 native locators and OCR keep working. `Go Back` closes the tab and returns to the app.
187- **Browser to app.** A web link that an app handles, such as a Play Store link, opens
188 that app. Its native elements are available as soon as it is in front.
189- **Choosing an app.** When more than one app can open a link, Android asks which one to
190 use. Answer with `Detect And Press` on the app's name, then on `Just once`.
191- **Other browsers.** Web locators read Chrome and WebViews with debugging enabled. If a
192 link opens in another browser, such as Samsung Internet, they fail with "Cannot read
193 the web page shown by …"; text locators and OCR work there. To keep a test in Chrome,
194 make Chrome the device's default browser.
195- **The same link twice.** Opening a link that an earlier tab still shows leaves two tabs
196 with the same address. When a web locator has already looked at the earlier tab, Optics
197 tells the two apart and uses the one on screen.
198- **A Custom Tab right after another.** When an app opens a Custom Tab just after one
199 closed, Chrome ignores the first tap on the new tab. Before typing into a field there,
200 press the field once.
201- **Covered elements.** When a banner, a dialog or a panel lies over the element a web
202 locator matches, Optics does not tap it, because the tap would land on whatever covers
203 it. Dismiss the cover first. `Get Text` still reads a covered element.
204
205On iOS, a link from an app opens in Safari or an in-app Safari sheet, and an app can
206show its own `WKWebView`. Web locators find elements in whichever of them is on screen.
207When an app shows several web views at once, a web locator finds its element in the one
208that holds it.
209To return from Safari to the app, use `Launch App` with the app's bundle id.
210
211## Chrome's own pop-ups
212
213A fresh Chrome shows native pop-ups over the page: a notification prompt, a sign-in
214offer, or terms to accept. While one is open, nothing on the page can be tapped. Grant the
215notification permission before opening Chrome so the prompt never shows:
216
217```csv
218module_name,module_step,param_1
219Prepare Chrome,Launch App
220Prepare Chrome,Execute Script,"{""script"": ""mobile: changePermissions"", ""args"": {""permissions"": ""android.permission.POST_NOTIFICATIONS"", ""appPackage"": ""com.android.chrome"", ""action"": ""grant""}}"
221```
222
223Dismiss any other pop-up with `Detect And Press` on its text or button id:
224`Stay signed out` or `signin_fre_dismiss_button` (sign-in offer), `No thanks` or
225`negative_button` (notification prompt).
226Give it a timeout of 5 seconds or more, because the prompt appears after the page loads.
227
228## WebViews in apps
229
230An app's WebView is reachable only when the app enables WebView debugging
231(`WebView.setWebContentsDebuggingEnabled(true)`), which debug builds usually do. Without
232it, web locators fail with "No web content found in the foreground app". Native
233locators and OCR still work on the WebView's content.
234
235Every app with WebView debugging on keeps a DevTools socket open, including apps in the
236background, and Android freezes background apps so their sockets stop answering. Optics
237keeps web lookups from waiting on those sockets:
238it starts Android sessions with `ensureWebviewsHavePages: false`,
239`enableWebviewDetailsCollection: false` and `extractChromeAndroidPackageFromContextName: true`
240(values in your `capabilities` take precedence), and it remembers the web context of each app
241instead of listing the device's contexts on every lookup.
242
243## Limits
244
245- Web locators search the top-level page only, not the inside of an `iframe`. Use text
246 locators or OCR for content in a frame.
247- When several Chrome tabs show the same address and Optics cannot tell them apart (three
248 or more, or two it has not looked at), web locators fail with "Cannot tell which
249 browser tab is on screen". Close the extra tabs.
250- Each web lookup, and each element listing with web content in front, switches context
251 twice and costs about one to two seconds on a remote device. Prefer native locators where they work, and use `css=` where they do not.
252- iOS sign-in sheets (`ASWebAuthenticationSession`) cannot be inspected. Use text
253 locators and OCR there.
254
255The `mobile_web` sample (`optics init --template mobile_web`) runs a Wikipedia search in
256Chrome with these steps.
