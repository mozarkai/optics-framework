338### Start signed in
339
340When a web flow signs in, the agent reads `optics://browser-profiles`. It lists
341the Chrome and Edge profiles on the machine that runs `optics mcp`, with the
342account in each:
343
344```json
345[{"channel": "chrome", "directory": "Default", "name": "Work", "email": "me@example.com"}]
346```
347
348The agent shows the list to the user and asks which profile to use. Then it
349passes the profile's `directory`, `name` or `email` as `capabilities.profile`:
350
351```json
352{
353 "driver": "playwright",
354 "capabilities": { "profile": "me@example.com" },
355 "app": "https://app.example.com"
356}
357```
358
359The browser starts with that profile's sign-ins. If the user picks no profile,
360the agent asks the user for the credentials and types them with `type_text`. A
361`profile` that matches no profile, or several, fails with `E0501` and lists
362them; pass `channel` (`chrome`, `chrome-beta` or `msedge`) to choose between
363browsers.
364
365A profile carries the sign-ins of the person who runs the server, so only a
366stdio server lists and accepts profiles. An HTTP server (`--transport http`)
367and `optics serve` refuse `profile`, and every API session refuses
368`user_data_dir`; set those in a project's `config.yaml` instead. See [Configuration](../configuration.md#driver-sources) for what a profile
369carries over.
