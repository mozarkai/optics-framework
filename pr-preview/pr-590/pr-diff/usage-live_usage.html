tt183### CSV or YAML
184
185`/save` follows the format your suite already uses. When every file in the project that
186defines test cases or modules is YAML, it saves YAML; a CSV project, a project mixing
187both, or a project with no suite files yet saves CSV. Add `csv` or `yaml` as a third
188argument to choose for one save:
189
190```text
191/save login_test login_module yaml
192```
193
194A YAML save writes the layout the runner reads:
195
196```yaml
197# modules/modules.yaml
198Modules:
199- login_module:
200 - Launch App
201 - Enter Text ${username_field} "test user"
202 - Press Element ${login_button}
203
204# test_cases/test_cases.yaml
205Test Cases:
206- login_test:
207 - login_module
208
209# test_data/elements.yaml (merged into when it exists)
210Elements:
211 username_field: //input[@id="user"]
212 login_button:
213 - loginBtn
214 - //button[@id='login']
215```
216
217Each step is one line of keyword and params. A param holding spaces or quotes is quoted
218so it reads back as the same single param (`text="Sign in"`, `"two words"`), and an
219element with several locators is written as its ordered fallback list, as
220`login_button` is above. Existing YAML files are merged
221into, not replaced: appending to a module that is already there adds the steps to its
222list, and anything else in the file is kept. Comments in a file `/save` rewrites are not
223preserved, since the file is re-serialised.
224
225A few recordings cannot be written as a YAML step, such as a param that holds both
226quote characters and a space; `/save` then fails without touching any file and asks you
227to save that module as CSV. The same all-or-nothing rule applies to a malformed target
228YAML file.
229
230**Saves are all or nothing.** In either format, every file's new content is built before
231anything is written, and each file is replaced in one step rather than rewritten in
232place. If a write fails partway (a full disk, a permissions error), the files already
233written are put back, so the project is never left with half a save and a retry doesn't
234hit a name conflict from one.
235
236**Appending across files.** A name the project already defines is a conflict in either
237format — a module in `modules/modules.csv` blocks `/save … yaml` under the same name
238too. Confirming the append only works when the existing definition is **only** in the
239file this save writes (`modules/modules.<ext>` / `test_cases/test_cases.<ext>`). The
240runner keeps one definition per name, so with a copy in any other file the appended
241steps could be replaced, or replace it, depending on load order; `/save` refuses and
242names the other file. Confirmations are tied to the format too: after a conflict on
243`/save … csv`, running `/save … yaml` asks again.
