tt1# Popup Rules
2
3Apps put popups in the way of a test: an offer, a rating request, a session warning. Without help, the step that
4needs the element behind the popup fails with `E0201`. With popup rules, a step that cannot find its element first
5checks the screen against your rules, runs the action you chose, confirms the popup is gone and looks again.
6
7A popup that no rule covers is never guessed at. The step stops with the evidence a rule can be written from.
8
9## How it works
10
111. A step looks for its element through every locator strategy and finds nothing.
122. Optics reads the page source once and tries the rules, lowest `priority` number first. The first rule whose
13 `detect` matches wins.
143. The rule's `action` runs (`tap`, `back`, `alert` or `none`). Optics then reads the screen again, waiting up to
15 5 seconds for the popup to go.
164. When it is gone, `then` decides what happens next: `retry_step` runs the step again, `fail_step` fails the step
17 and `stop_run` ends the run.
18
19A step that finds its element pays nothing: nothing is read and no rule is tried. The one exception is a rule with
20`check: before_every_step`, which costs one page-source read before each step that locates an element.
21
22Because the check runs only after the lookup failed, the step's own action never ran, so a retry cannot repeat a
23transfer or a tap.
24
25!!! note "Popup rules are off until you define one"
26 With no rules, nothing changes: no extra page-source reads and no `E0206`. The unknown-popup check below needs
27 at least one rule to be defined.
28
29## Where the rules go
30
31The rules are one list, in any of three places. They merge, and a later rule replaces an earlier one of the same
32name.
33
34| Where | When to use it |
35|-------|----------------|
36| `test_data/popup_rules.json` in the project folder | `optics execute` jobs. Found by its name, anywhere under the folder. It wins over a same-named rule in `config.yaml` |
37| `popup_rules` at the top of `config.yaml` or of a session's config | Live sessions and the REST API |
38| `Optics.add_popup_rules(rules)` (`Add Popup Rules` in Robot) | Library use |
39
40A rule list that cannot be read stops the run with `E0501`, naming the file and the rule, instead of quietly
41handling no popups.
42
43## Rule fields
44
45| Field | Values | Meaning |
46|-------|--------|---------|
47| `name` | text | Unique within the list |
48| `priority` | integer, lowest first | The first matching rule wins. Give sensitive rules the lowest numbers |
49| `detect.text_contains` | list of text | Any one, as a case-insensitive substring of the visible text. On iOS this includes the text of a system alert |
50| `detect.resource_id` | text | Android `resource-id`, matched exactly. On iOS use `detect.xpath` on the `name` attribute (the accessibility id) |
51| `detect.xpath` | text | An XPath over the page source |
52| `check` | `on_failure` (default), `before_every_step` | When the rule is tried |
53| `action.type` | `tap`, `back`, `alert`, `none` | `alert` is iOS only and answers a system alert, pressing the button named in `action.target` |
54| `action.target`, `action.fallback` | an xpath, a resource-id or visible text | Where to press. The fallback is tried if the target is not found. See [How a target is found](#how-a-target-is-found) |
55| `then` | `retry_step` (default), `fail_step`, `stop_run` | What happens after the action |
56| `sensitive` | `true` or `false` | Never acts: saves evidence, then ends the run |
57| `max_per_step`, `max_per_run` | integers, default 2 and 5 | Per-rule limits against a popup that keeps coming back |
58
59Every `detect` key you give must match. At least one is required. `tap` and `alert` need a `target`. A rule that
60retries the step needs an action that dismisses the popup, so `then: retry_step` with `action.type: none` is
61refused. A `sensitive` rule ignores its `action` and `then`.
62
63"Visible text" is the same text error detection reads: the `text`, `content-desc`, `label`, `value`, `hint` and
64`name` attributes of the page source.
65
66### A rule that sets every field
67
68```json
69[
70 {
71 "name": "Promotional offer",
72 "priority": 30,
73 "check": "on_failure",
74 "detect": {
75 "text_contains": ["Special offer", "Limited time"],
76 "resource_id": "com.example.bank:id/promo_banner",
77 "xpath": "//*[@resource-id='com.example.bank:id/promo_banner']"
78 },
79 "action": { "type": "tap", "target": "Not Now", "fallback": "com.example.bank:id/iv_close" },
80 "then": "retry_step",
81 "sensitive": false,
82 "max_per_step": 2,
83 "max_per_run": 5
84 }
85]
86```
87
88The file is plain JSON, so it cannot hold comments.
89
90## What a popup does to a step
91
92| Outcome | Step result | Code | Evidence kept |
93|---------|-------------|------|---------------|
94| Rule matched, popup gone, `retry_step` | Passes on the retry | none | Before and after screenshots |
95| A limit was hit | Fails, the test case ends | `E0207` | One screenshot per occurrence |
96| `fail_step`, or the popup stayed | Fails, the test case ends and the others run | `E0208` | Screenshot and page source |
97| `stop_run`, or a `sensitive` rule | The run stops | `E0208` | Screenshot and page source, nothing pressed |
98| A dialog is on screen and no rule covers it | Fails, the run continues, self-heal is skipped | `E0206` | Screenshot, page source and the first 200 characters of its text |
99| Nothing on screen | Fails as before | `E0201` or `X0201` | Nothing new. Self-heal runs if it is on |
100
101When a run stops, test cases that have not started are skipped. The suite teardown still runs, because it often
102closes the app.
103
104A step that fails with one of these codes is not retried with the next value of a `${variable}` locator list: the
105same popup would be in the way of every value.
106
107The popup check runs before AI self-heal. A matching rule costs nothing and does the same thing every run, while
108self-heal costs an LLM call and can press the wrong button.
109
110### How a target is found
111
112A `tap` target is looked for in the page source optics has just read: an xpath, a resource-id, or the exact visible
113text (ignoring case). When it is there, optics presses the centre of its bounds. This needs no other element source,
114so it works with `appium_find_element` alone. Only when the page source does not hold the target does optics ask
115the usual locators (text detection, image), which need their own sources enabled.
116
117### System alerts on iOS
118
119iOS keeps system alerts, such as a permission prompt, out of the app's page source. Optics reads them through the
120driver instead and adds them to the screen as an `XCUIElementTypeAlert` with one `XCUIElementTypeButton` for each
121button, so `text_contains` and `xpath` rules match them. Answer one with an `alert` action, which presses a button
122by its label. A `tap` cannot, since these buttons have no bounds in the page source.
123
124### Which dialogs count as a popup
125
126For `E0206`, optics looks for what only a dialog has: on Android an `alertTitle`, `parentPanel`, `button1` or
127`design_bottom_sheet` id, or a node from the system permission controller or package installer; on iOS an
128`XCUIElementTypeAlert`, `Sheet` or `Popover`. A screen with none of these is treated as having no popup.
129
130## Permissions
131
132Permissions are a session setting, separate from the rules. Optics grants or revokes each one right after the
133session starts, so the prompt never appears:
134
135```yaml
136permissions:
137 camera: allow
138 location: allow
139 notifications: deny
140```
141
142The setting sits at the top of the config, not inside the Appium capabilities, which are sent to Appium whole.
143
144- **Android.** Each permission is set with `mobile: changePermissions` (`pm grant` and `pm revoke`) for the
145 `appPackage` capability. The names are `camera`, `microphone`, `location`, `background_location`, `notifications`,
146 `contacts`, `calendar`, `phone`, `call_log`, `sms`, `storage`, `photos`, `videos`, `audio`, `bluetooth`, `nearby_wifi`,
147 `body_sensors` and `activity_recognition`; any full `android.permission.*` name works too. Some stand for several
148 permissions, and one the device's Android version does not have is skipped. An unknown name stops the start with `E0501`.
149 A permission the app does not declare cannot be changed. That is logged and the others are still set.
150- **iOS.** Nothing can be granted ahead of a prompt on a real device, so optics sets WebDriverAgent's
151 `autoClickAlertSelector` once and the prompt is answered the moment it appears. See [iOS](#permissions-on-ios).
152
153### Permissions on iOS
154
155WebDriverAgent answers every system alert by pressing the button whose label the setting names. It cannot tell which
156permission a prompt is for, so the names under `permissions:` do not matter on iOS, only the decision:
157
158| Decision | Buttons pressed |
159|----------|-----------------|
160| `allow` | `Allow While Using App`, `Allow`, `OK`, `Allow Full Access` |
161| `deny` | `Don’t Allow`, `Don't Allow`, `Keep Location Services Off` |
162
163- Every permission must be `allow`, or every one `deny`. A mix stops the start with `E0501`. To answer two prompts
164 differently, leave `permissions` out and use an `alert` rule for each.
165- The setting applies to every system alert, not only permission prompts, so an `OK` on any other alert is pressed too.
166- A prompt with no button in the table stays on screen. A popup rule can answer it, or the step fails with `E0206`.
167- After a denial an app can raise a second alert that offers `Turn On in Settings` or `Keep Location Services Off`.
168 The `deny` list holds the second, so the denial stays.
169- The labels are English. Another language needs an `alert` rule.
170- If the setting cannot be applied, optics logs a warning and the session carries on.
171
172To answer one prompt on its own terms, use a rule whose action is `alert`:
173
174```json
175{
176 "name": "Notifications prompt",
177 "priority": 5,
178 "detect": { "text_contains": ["to send you notifications"] },
179 "action": { "type": "alert", "target": "Allow" }
180}
181```
182
183Read this way, a rule written for `Allow While Using App` or `Allow Once` is matched on the alert's own text, for
184example `"text_contains": ["use your location"]`.
185
186A dialog that still appears, such as an OEM overlay, is caught by an ordinary text rule.
187
188## Covering the usual popups
189
190| Popup | Rule |
191|-------|------|
192| Promotional offer | `tap` "Not Now", with the close icon as `fallback` |
193| Rate Us | `tap` "Maybe Later" |
194| Session about to expire | `check: before_every_step`, `tap` "Continue Session". It does not wait for a failure, which a session timeout never causes |
195| Network unavailable | `tap` "Retry" with `max_per_step: 3`. When the retries run out the step fails with `E0207` and the run continues |
196| App update | Optional: `tap` "Later". Mandatory: a second rule with `action.type: none` and `then: stop_run`, with the lower `priority` number so it wins |
197| Permission | `permissions`, plus a text rule for a dialog that still appears |
198| Service unavailable | `tap` "OK" with `max_per_step: 2`, then the step fails with `E0207` |
199| What's New | `tap` "Close" |
200| A popup that keeps coming back | Not a rule: `max_per_step` and `max_per_run` end the loop |
201| Unknown or sensitive | A `sensitive: true` rule for a known one. An unknown one fails the step with `E0206` and presses nothing |
202
203## What a run records
204
205Every inspection leaves one `popup` event. The popup, the action, the time and the result are all in it. See
206[Event System](../architecture/event_system.md#popup-events) for the fields.
207
208- Without a runner (the `Optics` class or Robot), nothing publishes the events. Read them with
209 `Optics.get_popup_events()` (`Get Popup Events`), which returns one dict for each inspection, oldest first, and the
210 counts with `Optics.get_popup_summary()` (`Get Popup Summary`). Reading does not clear them.
211- One info log line for each handled, limited, stopped or unknown popup, with the rule, the action and the
212 milliseconds it took.
213- At debug level, one line for each rule tried that did not match.
214- At the end of the run, a summary counts each rule's handled, limit and stopped verdicts and lists every unknown
215 popup, so patterns show without reading every event.
216- Screenshots and page sources are saved in the run's output folder as `popup_<n>_before.png`,
217 `popup_<n>_after.png` and `popup_<n>_source.xml`. They need `save_captures` on. Screenshots also need a screenshot
218 source such as `appium_screenshot` in `elements_sources`; `appium_find_element` cannot capture the screen, so
219 without one a popup is still handled and the page source is still kept, but there are no images.
220
221## What is not covered
222
223- **Steps that do not locate an element.** Pressing by coordinates or percentage, swiping and scrolling skip the
224 lookup, so neither check sees them. A popup on screen takes their tap or swipe. A popup that appears during a
225 `Sleep` is caught at the next locating step.
226- **Running a module as the action**, such as logging in again, and **suggesting rules after a run**.
227- **Granting one iOS permission ahead of its prompt on a real device**, which Appium cannot do. The setting above
228 answers the prompt when it appears.
