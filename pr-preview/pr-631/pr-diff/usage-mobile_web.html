tt1# Mobile Web (browsers and WebViews on Android and iOS)
2
3Optics drives web pages on Android and iOS devices through the same Appium session that
4drives native apps. One test can open an app, follow a link into Chrome or Safari, fill a
5web form, and come back to the app, with no separate browser driver and no context
6switching in your test steps. The same test steps work on both platforms.
7
8## How it works
9
10The Appium session stays in the native context the whole time. Native locators (visible
11text, resource ids, native XPath) and OCR keep working on web pages, because Chrome and
12Safari put the page's text, links, inputs and buttons into the native UI tree.
13
14Web locators, `css=...` and DOM XPath such as `//button[@type='submit']`, go through the
15`appium_web` element source. For each lookup it:
16
171. finds the web content of the app in front and its front tab: Chrome or a debuggable
18 WebView on Android; Safari, an in-app Safari sheet (`SFSafariViewController`), an
19 inspectable `WKWebView` or another inspectable browser on iOS,
202. finds the element in the page and scrolls it into view, closing the on-screen
21 keyboard if it covers the element,
223. converts the element's position to screen coordinates, and
234. returns to the native context.
24
25The press or text entry that follows is a native action at those coordinates.
26
27## Configuration
28
29Enable `appium_web` next to the other Appium sources. `optics quickstart` and
30`optics configure` enable it for Android and iOS projects, and the MCP server includes it
31when it fills in the Appium sources for you.
32
33```yaml
34driver_sources:
35 - appium:
36 enabled: true
37 url: "http://localhost:4723"
38 capabilities:
39 platformName: Android
40 automationName: UiAutomator2
41 deviceName: emulator-5554
42
43elements_sources:
44 - appium_find_element:
45 enabled: true
46 - appium_page_source:
47 enabled: true
48 - appium_web:
49 enabled: true
50 - appium_screenshot:
51 enabled: true
52```
53
54Web lookups use a chromedriver that matches the Chrome version on the device. Let
55Appium download it by starting the server with
56`appium server --allow-insecure uiautomator2:chromedriver_autodownload`, or point
57`appium:chromedriverExecutableDir` at a folder of chromedriver binaries.
58
59UiAutomator2 driver 8.6.0 or later converts element positions exactly, including pinch
60zoom. Older drivers work too: Optics computes the position from the page's
61geometry and the on-screen bounds of the WebView. For an app that shows several
62WebViews, use 8.6.0 or later, so each element is placed in the WebView that holds it.
63
64### iOS
65
66The same `elements_sources` work with `platformName: iOS` and `automationName: XCUITest`.
67No extra driver is needed; XCUITest reads web pages through Safari's Web Inspector.
68
69- **Real devices:** turn on **Web Inspector** and **Remote Automation** in
70 Settings > Apps > Safari > Advanced. Simulators need no setup.
71- **Apps:** a `WKWebView` is readable when the app sets `isInspectable = true`, which
72 apps built with the iOS 16.4 SDK or later need even in debug builds. Safari and in-app
73 Safari sheets are always readable.
74- **Other browsers:** Chrome, Firefox and other iOS browsers are read the same way when
75 they allow inspection. Chrome needs Settings > Content Settings > Web Inspector.
76
77Optics starts native iOS sessions with `includeSafariInWebviews: true`,
78`additionalWebviewBundleIds: ["*"]`, `webviewConnectRetries: 1` and
79`webviewAtomWaitTimeout: 5000` (values in your `capabilities` take precedence). They let
80it see every app's web content and keep a lookup on a page that cannot answer to seconds
81instead of minutes. Sessions that start in Safari (`browserName`) keep Appium's defaults.
82
83Web positions on iOS are converted to screen points from a measurement of the page on
84screen, so Safari's toolbars, page zoom and the keyboard are accounted for.
85
86## Locators
87
88| Locator | Example | Resolved by |
89|---|---|---|
90| Visible text | `Sign in` | native tree, then OCR |
91| HTML id | `searchInput` | native tree (Chrome reports HTML ids as resource ids) |
92| CSS | `css=input[name='q']`, `#searchInput` | `appium_web` |
93| DOM XPath | `//button[@type='submit']` | native sources first, then `appium_web` (assertions skip the native sources for HTML-only paths) |
94
95An XPath that names an Android or iOS class (`android.widget.Button`,
96`XCUIElementTypeButton`) or a native attribute (`@resource-id`, `@content-desc`, `@text`,
97`@bounds`, `@clickable` and the other UiAutomator2 and XCUITest attributes) is left to the
98native sources. Text inside quotes does not count, so `//a[contains(@href,'android.com')]`
99is still a web locator. An assertion leaves an XPath whose path names only HTML
100elements (`//input[@name='email']`, `//button`) to `appium_web` alone; `//*` and other
101XPaths are still checked natively too. A web locator that matches an element hidden by the
102page (`display: none`, zero size) fails with "not displayed" instead of tapping blindly.
103A web locator that matches nothing fails at once, without waiting.
104
105`Assert Presence` with a web locator checks the DOM, so it passes for any element in the
106page, including one scrolled off screen or hidden. `Assert Visibility` passes only for an
107element that is displayed and inside the visible part of the page. An assertion checks
108every source that can take its locator in turn, round after round, until it passes or the
109timeout runs out, so the web check does not wait for the native sources to give up.
110
111## Screen elements
112
113`Get Interactive Elements`, `Get Screen Elements`, the MCP `elements` resource and the
114natural-language mode of `optics live` list the web page next to the app's native
115elements. With `appium_web` enabled, one call returns:
116
117- the native elements (Chrome's toolbar, the app around a WebView), as before;
118- every control and every piece of text of the web page, top to bottom, with screen-pixel
119 bounds. A sentence with links or bold words inside is one row, and the links get
120 their own rows; images, icons and canvases are listed too. Layout wrappers that hold
121 nothing of their own are left out. An element
122 outside the visible part of the page carries `offscreen: true`: scroll toward it, or
123 press it by locator, which scrolls it into view first;
124- a `loc` on each web element that the compact list reports (controls and visible
125 text): a `css=` or `xpath=` locator that matches only that element. Put it in your
126 elements file. The full list carries the same `loc` next to its `xpath`.
127
128The page's on-screen elements appear once. UiAutomator2 and XCUITest also show them in
129the native tree, without locators; the web entry replaces that copy.
130
131`loc` is built to stay the same from run to run. It uses, in order, a test attribute
132(`data-testid` and similar), a hand-written id, `name`, `placeholder`, `aria-label`,
133`title` or `alt`, a link's `href`, the element's own text, and a class. When those are
134shared, it names the element inside the card or row that holds it, for example
135`xpath=//article[.//h2[normalize-space()='Red Mug']]//button[normalize-space()='Add to cart']`.
136When nothing else is unique, it falls back to a CSS path. Generated ids and classes
137(`r-7f3a91c2`, `nav-help-83412`) are skipped. Text with digits, such as "Cart (0)", is
138matched by its leading words (`starts-with(normalize-space(), 'Cart (')`), so a count
139or a price that changes does not change the locator. The Playwright page source builds
140`loc` the same way.
141
142The listing adds about half a second on a local emulator, mostly finding and entering
143the page. On a screen with no web content, the cost is one check for web content.
144
145## Moving between apps and the browser
146
147Nothing in a test says which app is in front. Every lookup looks at the screen as it is
148now, so a test follows the user's path from one app to another:
149
150```csv
151module_name,module_step,param_1,param_2
152Read The Policy,Press Element,Google Play refund policy
153Read The Policy,Assert Presence,css=h1,30
154Read The Policy,Go Back
155Read The Policy,Assert Presence,Google Play refund policy,20
156```
157
158- **App to browser.** Tapping a link in an app opens Chrome or a Chrome Custom Tab, the
159 in-app browser most apps use. Web locators then find elements in the page in front, and
160 native locators and OCR keep working. `Go Back` closes the tab and returns to the app.
161- **Browser to app.** A web link that an app handles, such as a Play Store link, opens
162 that app. Its native elements are available as soon as it is in front.
163- **Choosing an app.** When more than one app can open a link, Android asks which one to
164 use. Answer with `Detect And Press` on the app's name, then on `Just once`.
165- **Other browsers.** Web locators read Chrome and WebViews with debugging enabled. If a
166 link opens in another browser, such as Samsung Internet, they fail with "Cannot read
167 the web page shown by …"; text locators and OCR work there. To keep a test in Chrome,
168 make Chrome the device's default browser.
169- **The same link twice.** Opening a link that an earlier tab still shows leaves two tabs
170 with the same address. When a web locator has already looked at the earlier tab, Optics
171 tells the two apart and uses the one on screen.
172- **A Custom Tab right after another.** When an app opens a Custom Tab just after one
173 closed, Chrome ignores the first tap on the new tab. Before typing into a field there,
174 press the field once.
175
176On iOS, a link from an app opens in Safari or an in-app Safari sheet, and an app can
177show its own `WKWebView`. Web locators find elements in whichever of them is on screen.
178When an app shows several web views at once, a web locator finds its element in the one
179that holds it.
180To return from Safari to the app, use `Launch App` with the app's bundle id.
181
182## Chrome's own pop-ups
183
184A fresh Chrome shows native pop-ups over the page: a notification prompt, a sign-in
185offer, or terms to accept. While one is open, nothing on the page can be tapped. Grant the
186notification permission before opening Chrome so the prompt never shows:
187
188```csv
189module_name,module_step,param_1
190Prepare Chrome,Launch App
191Prepare Chrome,Execute Script,"{""script"": ""mobile: changePermissions"", ""args"": {""permissions"": ""android.permission.POST_NOTIFICATIONS"", ""appPackage"": ""com.android.chrome"", ""action"": ""grant""}}"
192```
193
194Dismiss any other pop-up with `Detect And Press` on its text or button id:
195`Stay signed out` or `signin_fre_dismiss_button` (sign-in offer), `No thanks` or
196`negative_button` (notification prompt).
197Give it a timeout of 5 seconds or more, because the prompt appears after the page loads.
198
199## WebViews in apps
200
201An app's WebView is reachable only when the app enables WebView debugging
202(`WebView.setWebContentsDebuggingEnabled(true)`), which debug builds usually do. Without
203it, web locators fail with "No web content found in the foreground app". Native
204locators and OCR still work on the WebView's content.
205
206Every app with WebView debugging on keeps a DevTools socket open, including apps in the
207background, and Android freezes background apps so their sockets stop answering. Optics
208keeps web lookups from waiting on those sockets:
209it starts Android sessions with `ensureWebviewsHavePages: false`,
210`enableWebviewDetailsCollection: false` and `extractChromeAndroidPackageFromContextName: true`
211(values in your `capabilities` take precedence), and it remembers the web context of each app
212instead of listing the device's contexts on every lookup.
213
214## Limits
215
216- Web locators search the top-level page only, not the inside of an `iframe`. Use text
217 locators or OCR for content in a frame.
218- When several Chrome tabs show the same address and Optics cannot tell them apart (three
219 or more, or two it has not looked at), web locators fail with "Cannot tell which
220 browser tab is on screen". Close the extra tabs.
221- Each web lookup, and each element listing with web content in front, switches context
222 twice and costs about one to two seconds on a remote device. Prefer native locators where they work, and use `css=` where they do not.
223- iOS sign-in sheets (`ASWebAuthenticationSession`) cannot be inspected. Use text
224 locators and OCR there.
